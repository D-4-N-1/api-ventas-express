API de ventas

Referencia para consultar ventas consolidadas y registrar ventas desde una aplicación cliente.

En esta página Inicio y estado Configuración Consultar ventas Registrar venta Errores

Inicio y estado de las rutas

El servidor Express escucha en http://localhost:3000 por defecto. En producción, sustituye ese origen por el host publicado para la API.

El router se monta bajo /api/v1/ventas y las rutas también incluyen prefijos. Según el código actual, las rutas efectivas son:

OperaciónMétodoRuta efectiva
Consultar ventas consolidadasGET/api/v1/ventas/api/v1/ventas/consolidado
Registrar una ventaPOST/api/v1/ventas/api/v1/consolidado
Advertencia para integración: el servidor registra express.json() después del router. Por eso el cuerpo del POST no se procesa antes de la ruta y la lectura de req.body puede terminar en un error 500. La guía refleja la implementación actual; se recomienda corregir el orden del middleware antes de publicar el contrato a clientes. El POST también valida campos mediante valores truthy, por lo que rechaza cantidad: 0.

No hay autenticación ni CORS configurados en el código actual. El servidor tampoco define una ruta de salud.

Configuración del servicio

El servidor obtiene su configuración mediante variables de entorno:

VariableUso
PORTPuerto HTTP; opcional, por defecto 3000.
DB_HOST, DB_USER, DB_PASSWORD, DB_NAMEConexión del servidor a MySQL. No se envían desde la aplicación cliente.

La base de datos debe contar con los procedimientos almacenados db_ventas_tech y db_registrar_ventas. Las consultas usan JSON como formato de respuesta. Envía Accept: application/json; en las solicitudes POST usa también Content-Type: application/json.

Consultar ventas consolidadas

GET/api/v1/ventas/api/v1/ventas/consolidado

Recibe ambos valores como parámetros de consulta:

ParámetroRequeridoDescripción
sucursalSíValor de sucursal enviado al procedimiento db_ventas_tech.
anioSíAño enviado al procedimiento db_ventas_tech.
curl --get 'http://localhost:3000/api/v1/ventas/api/v1/ventas/consolidado' \
  --data-urlencode 'sucursal=1' \
  --data-urlencode 'anio=2026' \
  --header 'Accept: application/json'

Respuesta correcta · 200

Los campos de cada elemento los determina el procedimiento almacenado.

{
  "status": "success",
  "total_registros": 1,
  "data": [{}]
}

Parámetros incompletos · 400

{ "error": "Bad Request", "message": "Debe Enviar Ambos Parametros" }

Registrar una venta

POST/api/v1/ventas/api/v1/consolidado

El controlador espera estos campos en el cuerpo JSON:

CampoRequeridoDescripción
id_productoSíIdentificador del producto, según el esquema de base de datos.
id_clienteSíIdentificador del cliente, según el esquema de base de datos.
cantidadSíCantidad que se registrará; el valor debe ser truthy en la validación actual.
fecha_ventaSíFecha aceptada por el procedimiento almacenado.
curl --request POST 'http://localhost:3000/api/v1/ventas/api/v1/consolidado' \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/json' \
  --data '{"id_producto":10,"id_cliente":25,"cantidad":2,"fecha_venta":"2026-10-23"}'

Registro correcto · 201

{
  "status": "success",
  "message": "Venta registrada exitosamente",
  "datos_registrados": {
    "id_producto": 10,
    "id_cliente": 25,
    "cantidad": 2,
    "fecha_venta": "2026-10-23"
  }
}

Errores y códigos HTTP

CódigoCuándo ocurreRespuesta
400Falta sucursal o anio en la consulta.{"error":"Bad Request","message":"Debe Enviar Ambos Parametros"}
400Falta algún campo esperado por el POST (si el cuerpo llega parseado).{"error":"Bad request","message":"Todos los campos son obligatorios"}
500Falla una llamada a MySQL. El POST también puede llegar aquí porque el parser JSON se registra después de las rutas.Mensaje de error específico de la operación.

Ante errores 500, revisa la conexión y los procedimientos almacenados en el servidor. La API no expone detalles internos de MySQL al cliente.
